# 设计说明：ShopAdvisor 的决策模型为什么长这样

读者假设备：想改建议逻辑或权重，但又不想改完发现「怎么调都像在瞎调」。
运行方式、安装、常用旋钮见根目录 `README.md`；代码结构与工程约束见 `ARCHITECTURE.md`。

---

## 1. 要回答的三个问题，以及为什么它们互相纠缠

玩家站在商店里要做的决定其实只有一个：**这笔钱现在花在哪**。但它拆成三个界面：

1. 这 4 个栏位里，哪些值得买？
2. 要不要花金币重掷？
3. 要不要把某件锁住留到下一波？

单独回答第 1 问的计算器很好写（给每件打个分），但三个问题共享同一个约束 —— 钱包。
所以本 mod 的顺序是固定的：**先独立打分 → 再在预算内挑购买组合 → 用「买完剩下的钱」判刷新 → 把「值但不在这次组合里」的件交给锁定**。
任何一步换顺序都会产出矛盾建议，典型的是「三件都写着买，但钱只够买两件」和「建议买这三件 + 建议去刷新」（钱已经花完了）。

## 2. 形态选型：为什么是游戏内 Mod

| 备选 | 放弃理由 |
| --- | --- |
| 独立网页/CLI 计算器 | 需要玩家手抄局面（属性、金钱、刷价、栏位）。抄这四个数字的时间比自己想一遍还长，而且折扣、事件给的临时价、已刷新次数这些状态只有运行时才准。 |
| 解析存档 | Brotato 的存档只在波次间写盘，商店进行中的状态不在里面；且解析器要跟着存档格式变动。 |
| **游戏内 Mod** | 状态直接来自 `RunData` / `ShopItem`，无需人工转录。Brotato **官方内置 godot-mod-loader**，玩家只是把 zip 丢进 `mods/` 并勾选启用，没有前置安装。 |

一个刻意的边界：**只标注，不代点**。误推的代价由玩家承担，而且接管购买按钮会把 mod 和游戏 UI 结构强耦合，版本一更就失效。

## 3. 数据源选型

- fandom / BWIKI 的表停在 0.8.x，没跟上 Abyssal Terrors，**不用**。
- 用 [mojimoon/brotato](https://github.com/mojimoon/brotato) 里由游戏 `.tres` 反编译生成的
  `brotato_data.en.json` / `.zh.json`（跟随 DLC 更新）。`tools/fetch_data.py` 抓完后裁剪成
  `mod/data/brotato_data.json`（当前 257 武器 / 247 物品 / 64 角色 + 17 套武器职业套装 + 属性中文名）。
- **参考数据只做补充，不做真值来源**：效果与价格运行时直接读 `ShopItem.item_data` 和 `ShopItem.value`
  （后者已含折扣）。参考表的不可替代作用是三件事：中文名、档位/职业池（算刷新期望要遍历「这一档能刷出什么」）、
  武器基础伤害与 scaling（用来估 DPS）。
  带来的好处：游戏更新数值 → 只需重跑 `fetch_data.py`，一行代码不用改。

## 4. 价值模型：为什么是「相对档位标准件」，不是「值多少金」

最初的写法是拟合一个绝对尺度（1 分 = 1 金 = 1 有效 HP），但它标定不出来（第 7 节说明为什么标不出来）。
所以整个模型换成**比较**：每件物品算一个效用分 `score`，跟「本档位标准件」的分数线比。

```
anchor    = priors.tier_anchors[档位]            # 10 / 16 / 28 / 45 / 65（档位 0..4）
buy_thr   = max(anchor, anchor × k(wave))        # 买入门槛
maybe_thr = anchor × priors.maybe_factor         # 可考虑线（0.7）
k(wave)   = max(0.8, 1.2 − 0.02 × wave)
```

两个旋钮各管一件事，这点很重要，否则调参时两个作用会互相顶：

- **`tier_anchors` 管绝对增长**：波次越靠后，物品越贵、你越有钱，门槛跟着档位涨。
- **`buy_wave_scale` 管严格度**：同一个档位内，早期要求 1.2 倍标准件才叫「买」，到 20 波后退回 1.0 倍
  （被 `max(anchor, …)` 兜住）。早期的金币相对更稀缺、复利窗口更长，买一件杂货的机会成本最高，所以线抬得更严；
  后期机会成本低，线退回档位线本身。

标签的推出顺序（`advise_shop`）：

| 情况 | 标签 |
| --- | --- |
| 在本次推荐组合里，且 `score ≥ buy_thr` | **买** |
| `score ≥ buy_thr` 但不在组合里（买不起 / 预算让给了更值的组合） | **锁定** |
| 在组合里但没到 `buy_thr` | **可考虑** |
| 其余 | **跳过** |
| 价格 0 | 恒为**买**（白拿不占预算） |

「锁定」不是「其实可以买」的委婉说法 —— 它专门指 **买不起** 或 **预算被更值的组合拿走**，
理由行里会写明差多少金。锁定免费，所以只要这件值得留下就该锁，不需要它此刻买得起。

## 5. 单件的分数怎么算

```
score = u(属性效用) + dps_pct × weapon_dps_anchor − 负重惩罚
```

### 5.1 属性效用：一个属性一条曲线

`utility_from_stat_gain` 里每个属性有自己的曲线，但共享四个形状因子：

| 因子 | 含义 | 出处 |
| --- | --- | --- |
| 边际递减 | 已经堆得越多，每点越不值。护甲 `10/(10+已有)`、闪避 `25/(25+已有)`、百分比伤害/攻速/暴击 `100/(100+已有)` | 游戏里这些是加算进一个被乘算的比例，递减是可观察的 |
| 随波次 | 护甲/闪避每点随波次上涨（`base + per_wave × wave`）；采集、幸运、经验随波次衰减（前中期才值钱）；工程 12 波后腰斩（炮塔早已被替换） | 生存压力后期才显 |
| 随危险等级 | 生存类与输出类都乘 `danger_scale`（`1 + 0.04 × 危险等级`） | 门槛不随危险等级变，所以难局里同样的物品更容易过关 —— 这是刻意的：难局中一件能保命的东西确实比休闲局更值得花钱 |
| 随血条长度 | `hp_factor = max_hp/100`（夹在 0.6~1.5）：血越长，每点护甲/闪避折算的「等效减伤」越值钱 | 护甲按绝对值扣伤，血条是分母 |

**正负不对称**：同一属性作为代价出现时乘 `negative_stat_factor`（当前 1.2，代码里闪避的兜底默认是 1.5），
比好处更贵。
这不是数值洁癖 —— 游戏的物品确实靠「给 10 血但 −2 速度」这种笔成交，若两边等价则所有带副作用的物品都会被推成「买」。
护甲的负边另有一个下限 `armor_neg_kept_min`：已有护甲很高时递减因子会把负边压到几乎无害，但扣护甲在实战里照样疼。

**伤害类按流派占比加权**：`melee_damage` 乘 `melee_share`、`ranged_damage` 乘 `1 − melee_share`
（`melee_share` 由已装备武器的类型统计得出）。`elemental_damage` 固定 0.15 —— 它只对带元素标签的武器生效，
本机没法判断这个占比，宁可给个保守常数。

**武器 DPS**：`damage / max(1, cooldown) × scaling 乘区 × 全局百分比 × 各种属性加成`，
除以玩家当前 `total_dps` 得到**相对增益百分比**，再乘 `weapon_dps_anchor = 100`。
于是「+10% DPS ≈ +10 分」，武器和护甲第一次落在同一个可比的尺度上。
异流派武器（近战号拿远程枪）先乘 `off_type_factor = 0.35` 再计分，并在理由里写「非本流派武器」。

**非属性效果**（`+1 商店栏位`、范围、陷阱这类没有 `stat_` 前缀的）：`special_keys` 里有登记的按 `value × 权重`，
没登记的按 `special_bonus_per_effect = 4`/条，正向合计封顶 `special_bonus_cap = 16`，负向不封顶。
封顶是为了防止「一条特殊效果」把一件杂货顶成神件 —— 我们对这些效果的协同判断确实很粗糙（第 8 节）。

**诅咒物品**再减 `cursed_penalty = 25`：诅咒不只是属性表上那几行，它还绑着失败判定。

**武器职业套装**：参考表每把武器带 `sets`（如 `WEAPON_CLASS_BLADE`），17 个职业、每职业 5 档，
第 i 档 = 持有 i+1 把该职业武器时的**累计**加成。引擎只算增量
`set_gain = 套装累计(买后) − 套装累计(买前)`，再按普通属性曲线计分。
只取增量是因为「游戏是否已把套装加成并进 `RunData` 的属性汇总」本机确认不了 —— 取增量就不会重复计数，
两种情况下都只是略微保守。

### 5.2 负重

持有武器数超过 `loadout_penalty_start = 5` 后，每多一件扣 `loadout_penalty_per_slot = 12` 分。
这是「武器分数」唯一的减法项，因为 DPS 已经吃了伤害，重复的武器在 Brotato 里主要是负重惩罚而不是输出。

## 6. 为什么必须做组合选择

逐件独立判「买得起就买」会产出两类错：

1. **预算溢出**：四件都达标，钱只够两件 → 三条「买」里必然有假的。
2. **看不见替代品**：分数最高的那件反而不该买 —— 两件便宜的加起来边际价值更高；
   第二件同类护甲因为递减而不该叠。

做法（`choose_buy_set`）：候选 = 过了 `maybe_thr` 且单件买得起的件；在剩余金币内**穷举所有子集**（n ≤ 8，
商店正常只有 4 栏，所以 n ≤ 4）；每个子集按独立分从高到低逐件把内容并进玩家快照（`_snapshot_after`：
叠属性、叠武器 id、叠套装增量）后重估下一件的边际价值，累加成组合价值；同价值选花钱少的，把现金留给刷新和下一波。

组合价值是**固定顺序累加**的近似，不是全排列取最优。四件栏位下误差可忽略（README 第 5 节也写了这条）。

## 7. 权重从哪来：一次证伪 + 一次可用的标定

`_utility_stat_gain` 里那些系数最初全是拍的。本机有没有数据能校验它们？`tools/calibrate.py`
两种办法都试了，并把判决一起打印出来，就是为了避免以后有人拿同一批数据再拟合一遍就改权重。

### 7.1 用售价反推 —— 证伪

想法：拟合 `price ≈ Σ β·每点属性 + 档位底价`，读出的 β 就是「游戏认为 1 点该属性值多少金」。

实测：**档位哑变量单独就解释 R² = 0.88，加上全部属性点只多解释 2.3% 的价差**；
同一档位内「属性总点数 vs 售价」的 Spearman 只有 −0.22 ~ +0.29。
**Brotato 按档位定价，不按内容定价。** 于是逐属性 β 主要是共线性分摊出来的噪声
（`identifiability()` 会标出哪些属性从来没单独出现过，那种 β 连形状都不是），拿来调 priors 等于拿噪声调参。
脚本里的 `signal_check()` 会把这道门自己判一遍，不合格就不打印比值表。

### 7.2 用物品内部的兑换比 —— 可用

参考表 247 件物品里有 **115 件同时带正效果和负效果**，这就是设计者亲手写下的「用什么换什么」。
若一件物品给的好处和要的代价在它的价值度量里互相抵消，那么用我们自己的效用函数算
`正边效用 / 负边效用` 应当只是个常数；各件对这个常数的偏离就是权重误差。
把偏离对「属性出现位置」做一次岭回归（每属性一个 α，正边取正号、负边取负号），α 就是
「我们的权重相对设计者该乘 e^α」。这层信息是售价给不了的，因为它比的是**同一件物品内部**的两边。

两个必须知道的限定：

- **泛化检验**：α 只有在留出集（没参与拟合的物品）上也能压低残差才算数。控住档位后残差从 0.905 降到 0.606
  （−33%），不控时 −40%，但差的那部分属于「高档位物品两边都给得多」—— 那是档位效应不是权重误差，
  所以读**控档位**那一版。
- **只采用了一半**：符号在岭强度跨 3 个数量级（λ = 0.05→30）时全部稳定，但幅度随 λ 线性衰减 ——
  幅度是正则化决定的。因此按 e^(α/2) **半强度**采用，且**只采用 α < 0 的方向**
  （elemental 0.43、lifesteal 0.59、engineering 0.64、speed 0.72、hp_regeneration 0.74、ranged 0.82）：
  下调被高估的属性是把误推的杂货推到线下，方向安全。

拟合同时说 armor / dodge / percent_damage / crit 被我们**低估** 1.4~1.8 倍，**这条没有采用**：
我们的护甲分数本来就顶在买入门槛两倍以上的（+8 护甲 ≈ 103 分，档位门槛 ≈ 45 分），再抬只会让预算
选择器退化成「无脑挑护甲」。这种跨属性单位不统一是旧伤，而兑换比审计只量物品内部两边的比值、
量不到绝对尺度，所以它看不见这个后果。

结论写进 `priors.json` 的 `_stat_weight_adj_help`（含全强度 α 备查）。
`calibrate.py --check` 已经把这件事变成维护性断言：如果以后重新抓数据或改曲线，导致某个已采用的
修正方向被推翻，打包会直接失败并打印冲突项。

### 7.3 剩下没解的那一半：绝对尺度

**兑换比只给相对尺度，绝对尺度（一件 2 档物品该卖多少分）只能靠游戏内实跑定标**：
开 README 第 2 节的诊断落盘打一把，把 `shopadvisor_debug_w*.json` 拿回来跑 `ingest_debug.py`，
对着真实局面看建议有没有「明显不该买却买了」。那才是能动的下一个旋钮。

## 8. 承认不知道的事

- **未在游戏中实测**。开发机没有 Steam / Godot 3，GDScript 无法本机编译。核心逻辑靠「纯函数 + Python 同构实现 +
  用例回归」保证，UI hook 按 Bantato 等现成 shop hook 的真实字段写，仍需首次进游戏验证。
- 字段读取途径（属性、金钱、已刷新次数、档位）全是按常见写法**猜**的，都做了兜底与探测落盘。
- `set_first_count`（套装从第几把算起）两种读法本机无法区分，默认 2 是保守选择。
- 绝对金钱尺度未标定（见 7.3）。
- 角色天赋/被动不参与评分，只用汇总后的当前属性；怪物构成、ban 列表、队友协同同理（待接入）。
- 非属性效果只有粗略权重，缺协同判断。
- 刷新期望会把「刷出来也买不起」的高分件算进去 —— 因为锁定免费，刷到好件锁住、下波再买是本作的常规打法。
- 效用模型不是战斗模拟：它回答「这件相对本档位标准件值不值」，不保证最优解。
- 建议语言为中文；角标只读，不替你点击。
